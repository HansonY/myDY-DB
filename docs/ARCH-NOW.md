## 一条主线:只有 L0 不可再生

```
L0  抖音接口 ──f2──► videos.raw_z          2555 条完整响应(zlib)
    │                唯一不可再生:重采冒 403,媒体地址带 x-expires 会过期
    │
    │  纯 Python,零网络                    scripts/reproject.py
    ▼
L1  fragments                              5140 段等粒度文本
    │  overview 1781 · chapter 2402 · queries 970
    │
    │  bge-m3(本地,2.2GB)                scripts/build_index.py
    ▼
L2  frag_vec (sqlite-vec)                  5140 × 1024 维
    │
    ├──► L3  search   向量 KNN → 按作品折叠 → 三档分数      无状态
    │         └─► L4  answer   组上下文 → qwen-plus → 强制校验出处
    │
    └──► L5  insight  行为落差 + 标签共现图 + 干货率        无状态,快照留档
```

**L1–L5 全部可以随时全量重建**(秒级到分钟级),所以分块策略、嵌入模型、
阈值、分析口径都能随时改。反过来 **L0 一个字段都不能丢** —— 这就是
raw 压缩不剪枝的根据。

```

    cookie.py         扫码登录 / 读本机浏览器 cookie
    whoami.py totals.py
  service.py          采集编排:逐页落库 + 游标 + 跨进程锁 + 主动收手
  planner.py          每类决定 续采/增量/跳过 + 403 指数退避
  db/store.py    893  存取层 + raw 压缩层(对上层透明)
  knowledge/     1289 知识库,**不认识 collector**
    fragments.py 104  散字段 → 片段(纯函数,不碰库)
    embed.py     145  文本↔向量(可插拔:本地 bge-m3 / 云 DashScope)
    vecdb.py     114  唯一碰 sqlite-vec 的地方 + 指纹校验
    index.py     130  sync(只嵌新的)/ rebuild(换模型)
    search.py    137  KNN → 折叠 → 三档
    answer.py    136  组上下文 → LLM → 出处校验(纯函数可离线测)
    insight.py   523  行为落差 / 标签共现图 / 干货率 / 快照
```

依赖单向:

```
collector  → config                     只碰抖音
db/store   → config                     只碰库
planner    → db
knowledge  → db + embed(不认识 collector)
service    → collector + db             唯一同时认识两边的
入口三件   → service / knowledge
```

**`knowledge/` 和 `collector/` 互不相识**,所以知识库这一侧永远不碰抖音接口 ——
没有 403 风险,不需要锁,可以随便重跑。这是刻意划的边界。

## 关键选型(都是实测定的,不是照搬)

| 决定 | 依据 |
|---|---|
| 采集用 **f2** | 唯一现成带 ABogus 签名的;没签名裸请求返回 `status_code=8 用户未登录` |
| **不做 ASR** | 平台已给的字段榨干后 88% 的作品有可用片段;ASR 是 130 小时音频的活 |
| raw **压缩不剪枝** | 84 KB → 17 KB(4.9×),全库 209 MB → 43 MB,一个字段不丢 |
| **砍掉 FTS5 关键词路** | 实测向量全包了,关键词一条没救回来;极短查询用现成 LIKE 就够 |
| 嵌入用 **bge-m3** | 四个候选里唯一能中英互通(8 组话题里 4 组命中同一条,其余 0–1 组) |
| 向量留在 **sqlite-vec** | 5140×1024 KNN < 1ms;2555 条引 Qdrant 是浪费 |
| 分数**分三档不硬切** | 重叠带里有真结果;`good` 阈值 0.64 是扫出来的拐点(95% 准确) |
| 簇色**只用 3 个** | 配色验证器在本页底色上实测:4 色时黄↔橙红绿色盲 ΔE 4.8,硬失败 |
| 力导向用 **FR + 斥力截断** | 自己拍的常数会把节点全推到边界压成一条线 |

## `saved_at`:一个被实测推翻的计划

原计划写的是「游标就是时间戳,存下来就能做**深夜刷 vs 白天刷**」。动手前先量了一下,
**这个结论是错的**:

- 相邻两页游标间隔:收藏中位 **5.3 天**、点赞中位 **22.4 天**(最大 181 天)
- 而一页只有 ~19 条 → 一页内的条目根本分不出先后,小时级信号不存在
- 又把 raw 的 787 个字段逐个扫了一遍找逐条收藏时间:**没有**,
  只有合集/系列的创建更新时间,和「你什么时候存的」无关

所以时段分析做不了,能做的只剩**月级/季度级的兴趣漂移**。仍然要存,
因为它属于「不当场记就永久没有」那一类(和 `x-expires` 同性质),成本近乎零。

**语义是下界**:`saved_at` = 这条不早于这个时间被收藏;`saved_exact=1` 的是
每页最后一条,时间精确。落库时**只补不覆盖**(refill 重走时分页边界和首采不一样)。

**免费收紧一道**:你不可能收藏一个还没发布的作品,所以发布时间晚于游标时,
发布时间才是更紧的下界。实测首批 40 条里收紧了 16 条(中位 +5.1 天),
其中 **6 条因此从 7 月挪到 8 月** —— 不收紧的话 15% 会被算进错误的月份。

⚠️ **一个跨字段比较的坑**:`create_time` 存的是**本机本地时间且不带时区**
(`2026-07-17 10:47:29`),而 `saved_at` / `collected_at` / `updated_at` 都是
UTC 带 `+00:00`。直接用 SQL 比这两个字段会差 8 小时,而且日期相同时
`'T'`(0x54)和 `' '`(0x20)会让比较结果整个反过来 —— 必须走
`service._create_time_utc()`。

## 三个防静默出错的设计

这类 bug 最难查 —— 不报错,只是结果悄悄变错。

1. **`vec_meta` 记模型名。** 维度不符 sqlite-vec 会报错,但**同维度不同模型不会**
   (bge-m3 和 Qwen3-Embedding-0.6B 都是 1024 维)。换模型不重建索引,
   查询照跑、结果全是垃圾且看不出来 → 检索前比对指纹,不符直接拒绝。

2. **`content_state` 三态而非布尔。** `have` / `none`(抖音确认没给)/
   `unknown`(还没采全)。用 0/1 会把后两者混成同一个 0 —— 实测 1484 条
   「确认没有」和 771 条「还不知道」全标成 0,而前者该认命、后者该去补采。
   落库时**只升不降**:unknown 不能覆盖已确定的值。

3. **孤儿向量清理。** `fragments` 是先删后插重建的,rowid 会变 → 旧向量指向
   不存在的片段,**会被检索到却对不上原文**。这次写文档时就撞到了:
   `frag_vec` 5153 vs `fragments` 5140,跑一次 sync 清掉 1663 条孤儿。
