# 知识库检索:技术方案

片段层(L1)已经建好:**5153 段**,覆盖 1781 条作品,88% 的作品有可用片段。
这份文档只讲剩下两层怎么做 —— 检索(L2)和问答(L3)。

下面每个选型都是先跑数据再定的,不是照搬常见做法。

---

## 一、只走向量,不做关键词路(改过一次)

原方案是「FTS5 + 向量」混合。在真实数据上对比之后**砍掉了关键词路**。

我原来的理由是「向量对英文专名弱」。实测不成立:

| 查询 | 向量 | 关键词 | |
|---|---|---|---|
| Claude Code | 0.70/0.70/0.68 全对 | 全对 | 平手 |
| DeepSeek | 全对 | 全对 | 平手 |
| 肠易激 | 0.67 对 | 对 | 平手 |
| 穿越机 | 全对 | 第 3 条串到「特警无人机」 | **向量更好** |
| vibecoding | #1 错 | #1 **同样错** | 都没救 |

关键词路一条都没救回来。它唯一的短板补位场景(极短查询,如 `MCP` 只有 0.58)
**现成的 `LIKE` 搜索已经覆盖**,而且早就在界面上了:

```
MCP 6 条 · vibecoding 12 条 · Claude Code 7 条 · 穿越机 42 条 · DeepSeek 21 条
```

所以砍掉三个零件:二元组分词器、FTS5 索引、RRF 融合。
语义搜走向量,精确搜走现成的 LIKE,各司其职。

<details><summary>附:FTS5 的中文分词结论(留档,免得以后有人又提)</summary>

同一批文档同一批查询:

| 分词器 | 风控 | 赚钱 | 半导体 | 封装测试 | 斜杠命令 |
|---|---|---|---|---|---|
| `unicode61`(默认) | 0 | 0 | 0 | 0 | 0 |
| `trigram` | **0** | **0** | 1 | 1 | 1 |
| jieba + `unicode61` | **0** | 1 | 1 | 1 | 1 |
| 二元组 + `unicode61` | 1 | 1 | 1 | 1 | 1 |

`unicode61` 把整串中文当**一个** token,全军覆没。`trigram` 最少要 3 字,
两字词全废。jieba 输的原因很具体:「风控」不在词典里被切成「风/控」——
词典分词遇到领域新词就废,而这库里全是新词。二元组不要词典,所以最稳。

**真要做全文索引就用二元组**,代价是索引 343 KB → 3.1 MB(9 倍),查询 0ms。
</details>

## 二、语义路:sqlite-vec + bge-m3

### 向量库不外挂

`sqlite-vec` 实测可用(本机 `enable_load_extension` 是开的),
**5153 条 1024 维 KNN 查询 < 1ms**(512 维实测 0.7ms)。它是个小 wheel,不带 torch,不碰 f2 的依赖钉子。

单人 2554 条作品引 Qdrant/Milvus 是浪费,而零运维单文件是这个项目的地基。

### 模型选 bge-m3(双语)

要中英都支持,四个候选实测下来只有一个真能中英互通:

| 模型 | 大小 | 嵌入 5153 段 | **中英互通** | 中文分界 | 英文分界 |
|---|---|---|---|---|---|
| bge-small-zh-v1.5 | 92 MB | 4.1s | **0/8** | +0.061 | −0.073 |
| multilingual-e5-small | 470 MB | 6.0s | 1/8 | +0.017 | −0.010 |
| Qwen3-Embedding-0.6B | 1.2 GB | 48.8s | 1/8 | +0.026 | −0.038 |
| **bge-m3** | **2.2 GB** | **53s** | **4/8** | +0.025 | −0.026 |

「中英互通」= 用中文问和用英文问同一个话题,是否命中同一条视频(8 组话题)。
这是双语能力最直接的度量,bge-m3 是唯一及格的。

**代价说清楚**:
- 2.2 GB 模型(bge-small-zh 只要 92 MB)
- 嵌入 53 秒(bge-small-zh 4.1 秒)—— 仍是秒级,可接受
- **中文精度是有损失的**:阈值余量从 +0.061 降到 +0.025。
  换英文能力要付中文的钱,不是免费升级。

`multilingual-e5` 系列不能用:它把所有分数压进 0.78–0.92 的窄带,
阈值切不动(中文余量只有 0.017)。

英文能力的真实水平(bge-m3,库里有的话题):
```
0.712  how to practice English speaking  → B1水平升到C1的10技巧 ✓
0.678  semiconductor manufacturing       → 半导体工艺全知识点 ✓
0.631  why do people procrastinate       → 拖延症 ✓
0.598  how to fly an FPV drone           → 穿越机首飞 ✓
0.562  irritable bowel syndrome          → 述情障碍结婚 ✗ 错(库里明明有肠易激那条)
```
**英文比中文弱,会出硬错。** 所以英文查询要露分数,别让人当成确定答案。

模型是可换的:嵌入做成可插拔接口,向量是派生数据,重建只要 53 秒。
英文内容以后涨起来了、或出了更好的双语模型,换一行配置重跑就行。

### 一个必须解决的依赖冲突

`sentence-transformers` 会带 `huggingface-hub`,它要 `click>=8.4.2`,
而 **f2 钉死 `click==8.1.7`**。两者互斥,`pip check` 无论如何都不干净。

实测:装 `click==8.1.7` 时**两边运行时都正常** —— hf-hub 只在自己的 CLI 里
用 click,我们不用它的 CLI。

做法:嵌入依赖单独放 `backend/requirements-search.txt`,不进主依赖。
`setup.sh` 默认不装,想用语义检索再装。这样:
- 只做采集 + 关键词检索的人,依赖树干净、`pip check` 干净
- 要语义检索的人,明确知道自己在引入一个已知的钉子冲突(且已验证无害)

## 三、分数怎么用

### 分数分三档,不做硬切

原方案是「一个下限 0.58,低于就说没有」。实测发现硬切会切掉真结果:

```
库里有(中文)  0.653 – 0.743
库里有(英文)  0.562 – 0.712      ← 和下面重叠
库里没有       0.490 – 0.628
```

重叠带 0.54–0.59 里两种都有:`golf swing`(0.588)是噪音,
但 `mortgage rate calculation`(0.589)**其实找对了** —— 库里真有一条
700 万房贷的经历,是我把它标成「库里没有」标错了。

所以改成三档,把判断权交回给人:

| 分数 | 怎么呈现 |
|---|---|
| ≥ 0.62 | 直接给,当作相关结果 |
| 0.52 – 0.62 | 给,但标「可能相关」并**显示分数** |
| < 0.52 | 不返回。一条都没过线就明说「库里没有相关内容」 |

不设下限的后果我实测到了:问「怎么开价」,它自信地返回
「这个印钞机App,月入超过5万美金」。**一个会编答案的知识库比没有知识库更糟** ——
你会拿它当真。

诚实交代:阈值来自 8+6 组样本,而且我的「库里没有」标注本身出过错。
所以两个阈值都要可配,分数一律露出来,不做静默过滤。

### 按作品折叠

实测同一条作品的 overview 段和 chapter 段会同时命中,top3 里出现 3 条同一个
视频。召回时按 `aweme_id` 折叠,每条作品只出最高分的那一段,其余收进
「同一视频还有 N 段命中」。不删数据 —— 折叠是展示层的事。

实现:`backend/knowledge/search.py`

## 四、问答:MCP 加一个工具,强制带出处

```
ask_library(question, k=8)
  向量召回 → 按作品折叠 → 分三档
  → 没过线就直接回「库里没有」,并给出最接近的几条 + 分数,让人自己判断
  → 过线的组上下文(每段带 aweme_id + start_sec)
  → qwen-plus 回答
  → {answer, citations:[{aweme_id, author, url, at_sec, quote}], scores:[...]}
```

出处是硬要求:这些内容是刷视频刷来的,本来就该带着「谁说的、第几分钟说的」。
章节段有 `start_sec`,所以能精确到「第 12:30 处」。

网页端复用同一个接口做搜索框,不另建一套。

## 五、落地顺序

| 步 | 做什么 | 文件 | 验收 |
|---|---|---|---|
| 1 | 嵌入接口(可插拔,默认 bge-m3) | `knowledge/embed.py` | 全库 5153 段 53 秒嵌完 |
| 2 | 向量索引落进同一个库 | `schema.sql` + `knowledge/index.py` | KNN < 1ms;重建幂等 |
| 3 | 召回:三档分数 + 按作品折叠 | `knowledge/search.py` | 「怎么开价」返回「库里没有」而不是印钞机App |
| 4 | 三入口接上(语义搜与现成的精确搜并存) | `main.py` / `cli.py` / `mcp_server.py` | 同一查询三处结果一致 |
| 5 | `ask_library` 带出处 | `mcp_server.py` | 每条答案能点回原视频的具体时间点 |

**全程不碰抖音接口**,没有 403 风险,可以随便重跑。
索引和向量都是派生数据(源头 `raw_z` → `fragments`),
所以模型、阈值、折叠策略都能随时改,重建 53 秒。

## 六、明确不做

- **关键词路 / FTS5 / RRF**:实测向量全包了,关键词一条没救回来;
  极短查询用现成的 LIKE 就够(见第一节)
- **外挂向量库**(Qdrant/Milvus):2554 条对它们是浪费,零运维是地基
- **multilingual-e5**:分数压进 0.78–0.92 窄带,阈值切不动
- **硬阈值一刀切**:重叠带里有真结果,改三档 + 露分数
- **静默过滤低分结果**:分数必须露出来,不能假装「就这些」
- **ASR**:那 18% 太薄的片段才是它的目标,等这条路走到头再说
