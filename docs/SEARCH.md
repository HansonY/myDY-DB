# 知识库检索:技术方案

片段层(L1)已经建好:**5153 段**,覆盖 1781 条作品,88% 的作品有可用片段。
这份文档只讲剩下两层怎么做 —— 检索(L2)和问答(L3)。

下面每个选型都是先跑数据再定的,不是照搬常见做法。

---

## 一、关键词路:FTS5 + 二元组

### 默认分词器对中文是完全失效的

实测同一批文档、同一批查询:

| 分词器 | 风控 | 赚钱 | 半导体 | 封装测试 | 斜杠命令 |
|---|---|---|---|---|---|
| `unicode61`(默认) | 0 | 0 | 0 | 0 | 0 |
| `porter` | 0 | 0 | 0 | 0 | 0 |
| `trigram` | **0** | **0** | 1 | 1 | 1 |
| jieba 分词 + `unicode61` | **0** | 1 | 1 | 1 | 1 |
| **二元组 + `unicode61`** | **1** | **1** | **1** | **1** | **1** |

- `unicode61` 把整串中文当**一个** token —— 全军覆没。
- `trigram` 需要至少 3 个字,**两字词搜不到**。而「风控」「赚钱」「股票」这类
  两字词是中文里最常用的。
- **jieba 输给了二元组**:`风控` 不在它词典里,被切成「风/控」。词典分词
  遇到领域新词就废,而这个库里全是新词(vibecoding、穿越机、肠易激…)。
- 二元组不需要词典,所以没有未登录词问题。这也是 Lucene CJK 分析器的做法。

### 代价与收益(真实 5153 段实测)

```
原文 343 KB  →  FTS5 索引 3.1 MB      建索引 0.1s
查询延迟 0ms(「Claude Code」命中 20 段、「肠易激」5 段、「半导体工艺」3 段)
```

索引比原文大 9 倍 —— 二元组的固有代价(n 个字产生 n-1 个 token)。
3 MB 的绝对值完全不值得为此换方案。

### 它擅长什么、不擅长什么

擅长**专名**:`Claude Code` / `DeepSeek` / `MCP` / `肠易激`,字面精确、0ms。
这不是次要能力 —— 库里 30% 的片段夹着英文技术专名(claude 63×、agent 31×、
github 28×、deepseek 16×…),而**向量对专名恰恰是弱项**。

不擅长**换句话问**:实测「怎么开价」「带团队」都是 0 命中。这正是向量路的活。

实现:`backend/knowledge/tokenize.py`,一个 `bigram()` 函数,入库和查询用同一个。

## 二、语义路:sqlite-vec + bge-small-zh

### 向量库不外挂

`sqlite-vec` 实测可用(本机 `enable_load_extension` 是开的),
**5153 条 512 维 KNN 查询 0.7ms**。它是个小 wheel,不带 torch,不碰 f2 的依赖钉子。

单人 2554 条作品引 Qdrant/Milvus 是浪费,而零运维单文件是这个项目的地基。

### 模型选 bge-small-zh-v1.5,而不是多语言的 bge-m3

先看数据构成(5153 段):

```
纯中文              3481  68%
中文夹英文术语       1528  30%    ← claude / agent / github / deepseek / mcp
英文为主              133   3%
基本纯英文             11   0%
```

英文在这个库里是**中文句子里的技术专名**,不是英文文章。而专名交给 FTS5
比交给向量更准。所以不需要为 3% 的内容付多语言模型的代价
(bge-m3 是 2.2 GB,bge-small-zh 是 **92 MB**)。

实测性能:加载 24s(首次含下载)· 嵌入 **1262 段/秒** · 全库 5153 段 **4.1 秒**。

**如果以后英文内容涨到 20% 以上,再换 bge-m3** —— 向量是派生数据,
重建只要几秒,换模型没有迁移成本。这也是把嵌入做成可插拔接口的理由。

### 一个必须解决的依赖冲突

`sentence-transformers` 会带 `huggingface-hub`,它要 `click>=8.4.2`,
而 **f2 钉死 `click==8.1.7`**。两者互斥,`pip check` 无论如何都不干净。

实测:装 `click==8.1.7` 时**两边运行时都正常** —— hf-hub 只在自己的 CLI 里
用 click,我们不用它的 CLI。

做法:嵌入依赖单独放 `backend/requirements-search.txt`,不进主依赖。
`setup.sh` 默认不装,想用语义检索再装。这样:
- 只做采集 + 关键词检索的人,依赖树干净、`pip check` 干净
- 要语义检索的人,明确知道自己在引入一个已知的钉子冲突(且已验证无害)

## 三、融合:RRF,并且设相似度下限

### RRF 而不是加权求和

两路的分数不同量纲(BM25 是负数且无上界,cosine 在 0–1),
线性加权要调权重,而且换了模型就得重调。RRF 只用排名:

```
score(d) = Σ 1 / (60 + rank_i(d))
```

不需要调参,对量纲不敏感。

### 相似度下限:这一条比融合本身更重要

实测 8 个「库里有」的话题 vs 8 个「库里没有」的话题,取各自最高相似度:

```
库里有    0.618 – 0.719    (拖延症 · 半导体 · AI Agent · 肠胃 · 英语口语 · 炒股风控 · 育儿 · 穿越机)
库里没有  0.407 – 0.560    (给客户开价 · 带团队 · 挑红酒 · 高尔夫 · 房贷 · 养马 · 焊接 · 考公)
```

**可分,间隔 0.058。** 所以设一个下限(先用 **0.58**),低于它就直接说
「库里没有相关内容」。

不设下限的后果我实测到了:问「怎么开价」,它自信地返回
「这个印钞机App,月入超过5万美金」(0.524)、「大宗商品涨价顺序」(0.514)。
**一个会编答案的知识库比没有知识库更糟** —— 你会拿它当真。

诚实交代:16 个样本、间隔只有 0.058,所以下限要可配,而且**分数要露给用户看**,
不做静默过滤。

### 按作品折叠

实测同一条作品的 overview 段和 chapter 段会同时命中,top3 里出现 3 条同一个
视频。召回时按 `aweme_id` 折叠,每条作品只出最高分的那一段,其余收进
「同一视频还有 N 段命中」。不删数据 —— 折叠是展示层的事。

实现:`backend/knowledge/search.py`

## 四、问答:MCP 加一个工具,强制带出处

```
ask_library(question, k=8)
  混合召回 → 按作品折叠 → 过下限
  → 没过线就直接回「库里没有」,并给出最接近的几条 + 分数,让人自己判断
  → 过线的组上下文(每段带 aweme_id + start_sec)
  → qwen-plus 回答
  → {answer, citations:[{aweme_id, author, url, at_sec, quote}], scores:[...]}
```

出处是硬要求:这些内容是刷视频刷来的,本来就该带着「谁说的、第几分钟说的」。
章节段有 `start_sec`,所以能精确到「第 12:30 处」。

网页端复用同一个接口做搜索框,不另建一套。

## 五、落地顺序

| 步 | 做什么 | 文件 | 验收 |
|---|---|---|---|
| 1 | 二元组分词 | `knowledge/tokenize.py` | 上面那张分词器对比表跑出同样结果 |
| 2 | FTS5 索引 | `schema.sql` + `knowledge/index.py` | 5153 段 → 3 MB,「Claude Code」命中 20 |
| 3 | 嵌入接口(本地/云可插拔) | `knowledge/embed.py` | 全库 4 秒嵌完 |
| 4 | 向量索引 | `knowledge/index.py` | KNN < 1ms |
| 5 | 混合召回 + RRF + 下限 + 折叠 | `knowledge/search.py` | 「怎么开价」返回「库里没有」而不是印钞机App |
| 6 | 三入口接上 | `main.py` / `cli.py` / `mcp_server.py` | 同一查询三处结果一致 |
| 7 | `ask_library` 带出处 | `mcp_server.py` | 每条答案都能点回原视频的具体时间点 |

第 1–5 步**全程不碰抖音接口**,没有 403 风险,可以随便重跑。

索引和向量都是**派生数据**,源头永远是 `raw_z` → `fragments`。
所以分词策略、模型、下限都可以随时改,重建只要几秒。

## 六、明确不做

- **外挂向量库**(Qdrant/Milvus):2554 条对它们是浪费,零运维是地基
- **jieba 分词**:实测输给二元组,而且引入词典维护
- **bge-m3**:2.2 GB 换 3% 的英文内容,不值;英文专名 FTS5 更准
- **线性加权融合**:要调参、换模型要重调,RRF 不用
- **静默过滤低分结果**:分数必须露出来,不能假装「就这些」
- **ASR**:那 18% 太薄的片段才是它的目标,等这条路走到头再说
