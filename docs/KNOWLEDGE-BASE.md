# 从「能搜的收藏夹」到知识库

## 现在差在哪

已经有的:2552 条作品、完整原始响应、互动数据、官方三级分类、话题标签、
关键词检索、三个入口(网页 / 命令行 / MCP)。

但它还不是知识库,差三件事 —— 而且是有依赖顺序的:

| | 缺什么 | 现状实测 |
|---|---|---|
| **内容** | 大部分作品**没有文本内容** | 只有 299 条(12%)有平台 AI 总结。文案有 2511 条,但那是作者写的标题/营销话术,不是视频讲了什么 |
| **结构** | 有内容的也只是一大段话 | 拿不出「这条教程的步骤是什么」「这条观点的论据是什么」 |
| **检索** | 只能按字面找 | `LIKE '%谈判%'` 找不到讲「怎么开价」的那条。问「我收藏过的关于带团队的说法有哪些分歧」完全无解 |

顺序不能颠倒:没有内容,结构化就是给标题做结构化;没有结构,语义检索召回的
是整段大文本,塞不进上下文也不好引用。

## L1 内容层:把视频变成文本

### 结论先说:走 ASR,并且只做该做的那部分

先排除了两条更便宜的路,都是实测排除的:

- **平台字幕**:`is_subtitled` 有 50% 的作品是 1,一度以为 raw 里能捞到字幕文本。
  抽 18 条逐字段翻完 —— 没有。`caption` 只是文案重复,`caption_start/end` 是
  话题标签在文案里的字符偏移。**这条路不存在。**
- **@豆包 评论区**:要对每条作品自动发评论。批量写操作是封号主因,已否决。

### 音频从哪来:`music_url`,不是视频

| 路线 | 全库 130 小时的代价 | 备注 |
|---|---|---|
| 下整段视频 | **50.3 GB** | 112.7 KB/s |
| 只下音轨 `music_url` | **11.9 GB** | 26.8 KB/s,而且直接是 `audio/mpeg`,**不用 ffmpeg 转** |

**实测过的两个关键前提:**

1. **90% 的作品用「原声」** —— `music_title` 形如「@某人创作的原声」,那就是作者
   本人说话的那条音轨,ASR 拿到的正是内容。剩下 10% 用的是商用 BGM /
   热门音乐,`music_url` 下来是配乐,**ASR 毫无意义** → 这部分必须回落
   `play_url` + `ffmpeg -vn` 抽音轨。判断依据就是 `music_title` 里有没有
   「创作的原声」。
2. **两天前采的地址现在还能下** —— 抽 5 条,音轨和视频都返回 `HTTP 206`
   (支持 Range)。`play_url` 大多不带 `x-expires`。
   但**不能赌它永久有效**:封面就是活生生的例子(抢救时已有 5 张失效)。
   所以采集时就该顺手落音轨,而不是等要用了再说。

### 只做该做的:305 条,不是 2552 条

对全库做 ASR 是 130 小时音频。但知识价值极度集中 —— 用**现成的免费信号**
(官方分类 + 时长 + 是否原声)就能筛,不必先花代价做完才知道该不该做:

```
筛子:官方分类 ∈ 知识类  AND  时长 ≥ 60s  AND  还没有平台总结  AND  是原声
结果:305 条 · 27.7 小时音频 · 下载 ≈ 2.6 GB · M5 Pro 上约 1.8 小时跑完
```

对照被筛掉的:`随拍` 270 条、`影视` 93 条、`萌宠` 42 条 —— 这些做了 ASR
也进不了知识库。而 `人文社科` 124 条占了 32.6 小时(平均 16 分钟/条),
是密度最高的一块。

> 注:现在有 801 条显示「(未分类)」,那是点赞里还没回补完整字段的 769 条 ——
> 回补完这个筛子会更准,所以 ASR 应该排在回补之后。

### 技术实现

```
scripts/asr.py  —— 新增
  1. 选题:上面那个 SQL 筛子,--limit 控制单轮量
  2. 取音轨:原声 → music_url 直下 mp3
             商用BGM → play_url 下 mp4,ffmpeg -vn -ar 16000 -ac 1 抽单声道
     落到 data/audio/<aweme_id>.mp3,已存在就跳过(幂等)
  3. 转写:mlx-whisper(Apple Silicon 上 Metal 加速,M5 Pro 实测量级 ~15× 实时)
             模型 large-v3-turbo,language="zh" 显式指定(不指定会误判方言)
  4. 落库:store.save_transcript(aweme_id, "asr", text, {"tier":2, "model":..., "sec":...})
             带 segments(时间戳)→ store.save_extraction(category="asr_segments")
  5. 断点:transcripts 主键是 (aweme_id, kind),重跑天然幂等;
             失败记进 collect_runs 风格的 asr_runs,不阻塞后续条目
```

依赖:`pip install mlx-whisper`(ffmpeg 已装)。**不碰 f2 的钉子**:
mlx-whisper 不依赖 pydantic/httpx,和 `pydantic==2.9.*` 无冲突。

**为什么不用云 ASR**:130 小时按主流定价是三位数人民币,而本机跑是电费。
更重要的是音频要上传到第三方 —— 这些是私人收藏。

## L2 结构层:把文本变成可组合的知识

一段 2000 字的转写文本,用处只比没有强一点。要能回答「步骤是什么」,
得先把它拆成字段。

### 已有的地基

`extractions` 表已经在了:`category / title / summary / fields_json / model / tier`。
现在只用来存平台给的章节大纲(`category='chapters'`, `tier=0`)。tier 的含义
已经定好:0=平台直给、1=文案、2=关键帧+视觉、3=整段视频 —— ASR 归 2。

### 分类型抽取,而不是一把梭

统一 schema 抽不出有用东西。按内容类型分:

| 类型 | 抽什么 |
|---|---|
| 教程 / 操作 | 目标 · 前置条件 · 有序步骤 · 材料或工具 · 常见坑 |
| 观点 / 分析 | 核心主张 · 论据 · 反方 · 适用边界 |
| 工具 / 产品 | 名称 · 解决什么问题 · 怎么获取 · 替代品 |
| 事实 / 科普 | 结论 · 机制 · 数据出处 |
| 清单 / 推荐 | 条目数组 · 每项一句话理由 |

类型判断用官方分类 + 转写开头做先验,让模型选,不要人工枚举规则。

### 模型:qwen-plus(已有的 DashScope 通道)

- 只对**有内容的**做:299(平台总结)+ 305(ASR)= 604 条,不是 2552 条
- 平均输入按 1500 token 算,604 条一轮约 90 万 token —— 一次性成本很低
- **必须做版本闸门**:`extractions` 加一列 `prompt_version INTEGER`。
  提示词或 schema 改了就 +1,版本不符的重新生成、**永不迁移旧数据**。
  (不加这个,半年后库里会混着三代格式的 `fields_json`,谁都不敢用。)
- 幂等:主键已经是 aweme_id,重跑覆盖

```
scripts/extract.py  —— 新增
  取 transcripts 里 kind in (summary, asr) 的文本
  → qwen-plus 结构化(response_format json)
  → store.save_extraction(..., tier=2, prompt_version=N)
  --force 忽略版本重做;默认只做版本不符或缺失的
```

## L3 检索层:从按字面找,到能回答

### 混合检索,不是纯向量

纯向量对精确词很差 —— 问「M5 Pro」「bge-m3」这类型号/专名,向量会召回
一堆「差不多」的东西。所以两路召回后融合:

```
关键词路:SQLite FTS5(编译进去的,不用扩展)对 desc + summary + asr 建索引 → BM25
语义路:  sqlite-vec 存向量 → cosine
融合:    RRF(倒数排名融合),不用调权重,比线性加权稳
```

**已实测**:本机 Python 3.13 的 sqlite3 `enable_load_extension` 可用,
FTS5 也在 —— 所以**向量检索能留在这个单文件库里**,不必引 Qdrant/Milvus。
2552 条对独立向量库是浪费,零运维单文件才是这个项目的价值。

### 分块

- **有章节大纲的 300 条**:章节边界就是天然分块点,还自带时间戳 →
  引用时能直接给「这条视频的 12:30 处」
- **ASR 的**:按时间窗切(~400 字 / 30 秒重叠),保留起止秒数
- 每块存 `chunks(aweme_id, idx, start_sec, end_sec, text, vec)`

### Embedding

| 选项 | 取舍 |
|---|---|
| 本地 `bge-m3` | 零成本、不出网、中文好;首次下模型 ~2 GB |
| DashScope `text-embedding-v3` | 免部署、维度可选;要出网、按量付费 |

推荐**本地 bge-m3**:和 ASR 一样的理由 —— 私人收藏不出机器,而且要重建索引时
不心疼(改了分块策略就得全量重算,按量付费会让人不敢改)。

### 问答入口:MCP 加一个工具

```
ask_library(question, k=8)
  混合召回 k 块 → 组上下文(每块带 aweme_id + 时间戳)
  → qwen-plus 回答,**强制带出处**
  → 返回 {answer, citations:[{aweme_id, author, url, at_sec, quote}]}
```

出处是硬要求。知识库最大的失败模式是给出一个听着对、但查不到来源的答案 ——
这些内容是刷视频刷来的,本来就该带着「谁说的、在第几分钟说的」。

网页端同一个接口做个搜索框即可,不必单独建一套。

## 落地顺序

| 阶段 | 做什么 | 前置 |
|---|---|---|
| **P0** | 回补点赞剩余 769 条 | 无。不补完,ASR 的筛子会漏掉一大批(801 条还没分类) |
| **P1** | ASR 305 条(2.6 GB / ~1.8 h) | P0 |
| **P2** | FTS5 + sqlite-vec + 混合检索 + `ask_library` | P1(有内容才值得建索引) |
| **P3** | 结构化抽取 604 条 + `prompt_version` 闸门 | P1 |

P2 和 P3 可以并行 —— 检索靠原文就能建,结构化是另一条增量。

**明确不做:**

- 下整段视频(50 GB vs 12 GB,除了极少数需要看画面的)
- 对 2552 条全做 ASR(一半是随拍/影视/萌宠,做了也进不了知识库)
- 引独立向量库(单人 2552 条,sqlite-vec 够;零运维是这个项目的地基)
- 云 ASR / 云 embedding 跑全量(私人内容 + 重建索引时不敢改)
- 任何写操作(评论、点赞、关注)—— 封号主因,这条永远不变

## 一个必须一起处理的问题:重复

2552 条里同主题重复很多(热门内容会被反复推)。不去重的话,语义检索
top-8 里可能有 5 条讲同一件事,等于把上下文浪费掉。

最省的做法:向量建好之后跑一次相似度聚类(阈值 0.92 起),同簇的在检索时
只出代表条目、其余折叠展示。不删数据 —— 和 raw 一样的原则,**折叠是展示层的事**。
